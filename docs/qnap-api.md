# QNAP management API reference

What this plugin talks to, and the traps that cost the most time to find.
Everything here was verified against a TS-873A running QuTS hero h5.3.4.

## Provenance

This document describes observable behaviour of an interface, written from
scratch. It exists so that the plugin can interoperate with a QNAP NAS, and so
that anyone maintaining the plugin can check what it does and why.

It was compiled from:

- the usage strings that `/sbin/iscsi-restful` prints about itself, read on a
  NAS owned by the author
- QNAP's own CSI driver for Kubernetes, which QNAP publishes under Apache-2.0
  ([qnap-dev/QNAP-CSI-PlugIn](https://github.com/qnap-dev/QNAP-CSI-PlugIn))
- HTTP exchanged between that driver and the author's own NAS
- HTTP exchanged between the QNAP web interface and the author's own NAS

No QNAP code or data is reproduced here.

## Transports

There are three, and each operation only works on one of them.

| Transport | Base | Session id |
| --- | --- | --- |
| REST | `https://<nas>/api/...` | `sid: <sid>` **header** |
| CGI | `https://<nas>/cgi-bin/...` | `&sid=<sid>` query parameter |
| login | `https://<nas>/cgi-bin/authLogin.cgi` | — |

Getting a session:

```sh
curl -sk https://<nas>/cgi-bin/authLogin.cgi \
     -d "user=<user>" --data-urlencode "pwd=$(printf '%s' "$PW" | base64)"
# -> <authSid><![CDATA[........]]></authSid>

curl -sk -H "sid: $SID" https://<nas>/api/iscsi/v1/luns
```

Notes that cost time:

- The session id **only** works as a `sid:` header on REST. `X-SID`,
  `Authorization: Bearer` and cookies all return
  `{"error_code":-22,"error_message":"sid is invalid."}`.
- REST lives at `/api/...`. Prefixing it with `/cgi-bin/` returns 404.
- Port 8080 redirects to 443, so use HTTPS directly.
- An expired session is reported as **HTTP 200** with `error_code -22`, so the
  body has to be inspected rather than the status code.
- QNAP's own CSI driver sends credentials in the **query string**, where they
  end up in access logs and error messages. Use a POST body instead.

## Creating a LUN

A LUN is created through the **storage** API, not the iSCSI API.

```json
POST /api/storage/v1/volumes
{
  "label": "vm-100-disk-0",
  "type": "zvol",
  "pool_id": 2,
  "capacity": 1073741824,
  "provision_type": "thin",
  "threshold": 80,
  "iscsi": { "create_lun": true },
  "zfs": { "compress": true, "dedup": false, "fast_copy": false, "record_size": 16384 },
  "read_cache_enable": true,
  "sync_io": 0,
  "snapshot_reservation": 0,
  "encryption": { "encrypt": false, "key_str": "", "save_key": false, "use_default_key": false }
}
-> {"single": {"volume_id": 20}, "error_code": 0, "error_message": "Success"}
```

- `capacity` is in **bytes** here, unlike the iSCSI API which reports whole GB.
- `iscsi.create_lun` makes the NAS register the LUN in the same call.
- Creation is asynchronous. Poll `GET /api/storage/v1/volumes` until the volume
  has `creating: false` and a `lun_index >= 0`.
- The zvol name, `lun_naa`, serial number and `t10_dev_id` are all assigned by
  the NAS. Nothing needs to be generated by the client.

### Option mapping

Every field below was confirmed to reach the corresponding ZFS property.

| Field | ZFS property |
| --- | --- |
| `zfs.compress` | `compression` (**LZ4 only**, no zstd) |
| `zfs.dedup` | `dedup` |
| `zfs.record_size` | **`volblocksize`** |
| `zfs.fast_copy` | `fastcopy` |
| `read_cache_enable` | `secondarycache` |
| `sync_io` | `sync` — **0 standard, 1 always, 2 disabled** |

`volblocksize` cannot be changed after creation.

## Mapping a LUN to a target

```
POST   /api/iscsi/v1/targets/:target_index/luns/:lun_index    map
DELETE /api/iscsi/v1/targets/:target_index/luns/:lun_index    unmap
```

The target index is resolved from the IQN via `GET /api/iscsi/v1/targets`, which
also reports the initiators currently connected — useful for a health check.

Once mapped, the LUN appears on the initiator as
`/dev/disk/by-id/scsi-3<lun_naa>` after an `iscsiadm -m session --rescan`.

## Resizing

```json
PUT /api/storage/v1/volumes/:volume_id/reshaping
{"capacity": 8589934592, "iscsi": {"update_lun": true}, "provision_type": "thin"}
```

**Do not use `PUT /api/iscsi/v1/luns/:lun_index` with `lun_capacity`.** It
returns `error_code 0` and changes what the API reports, but leaves the zvol at
its original size. The same endpoint also silently ignores `sync`. Treat that
endpoint as unable to touch anything backed by the dataset.

Sibling sub-resources that do work:

```
PUT /api/storage/v1/volumes/:id/label        {"label": "...", "iscsi": {"update_lun": true}}
PUT /api/storage/v1/volumes/:id/threshold    {"threshold": 80, "iscsi": {"update_lun": true}}
PUT /api/storage/v1/volumes/:id/read_cache   {"enable": false}
```

## Snapshots

Snapshots have their own REST API. The `snapshot.cgi` endpoints still work but
the web interface no longer uses them.

```
GET    /api/snapmgr/v1/volumes/:volume_id/snapshots     list
POST   /api/snapmgr/v1/volumes/:volume_id/snapshots     create
DELETE /api/snapmgr/v1/snapshots/:snapshot_id           delete
POST   /api/snapmgr/v1/snapshots/:snapshot_id/recovery  roll back
GET    /api/snapmgr/v1/system/background/jobs           running jobs
```

Creating:

```json
POST /api/snapmgr/v1/volumes/20/snapshots
{"snapshot_name": "snap1", "snapshot_description": "...", "vital": 0, "expire_min": 0}
```

- `expire_min` **must be 0**. QNAP's own CSI driver passes 30, which makes
  snapshots disappear half an hour later.
- `vital: 1` marks the snapshot as protected in the web interface.
- Deletion is asynchronous and takes a few seconds to become visible.

### Rollback

```
POST /api/snapmgr/v1/snapshots/:snapshot_id/recovery?stop=false&save_key=false
-> {"single": {"fork": 1}, "error_code": 0, "error_message": "Success"}
```

- `fork: 1` means a background job was started. It took about 10 seconds in
  testing; the reply says nothing about completion.
- **Every snapshot newer than the target is destroyed**, which is normal ZFS
  behaviour — but the NAS does it without any warning or confirmation. A client
  has to guard against this itself. This plugin implements
  `volume_rollback_is_possible` so PVE refuses the operation and names the
  snapshots that are in the way.
- If a clone depends on a newer snapshot, the NAS *does* refuse, and helpfully
  names the culprit:

  ```json
  {"error_data": {"cloned_snapshots": "snap2"},
   "error_code": -619, "error_message": "Failed to recover due to cloned snapshot"}
  ```

  This also means taking a "just in case" clone before a rollback makes the
  rollback impossible.

## Cloning

There are two clone operations and they behave completely differently.

| CGI function | Result |
| --- | --- |
| `clone_qsnapshot` | independent volume, **full copy** |
| **`instant_clone_qsnapshot`** | **copy-on-write clone** |

```
GET /cgi-bin/disk/snapshot.cgi?func=instant_clone_qsnapshot
      &snapshotID=<id>&new_name=<name>&poolID=<pool>&targetIndex=<target>&by_lun=1&sid=<sid>
-> <result>0</result>
```

Measured on an 8 GiB volume:

```
zfs276  8G  176K   origin=-                     <- clone_qsnapshot
zfs277  8G  16.0K  origin=zpool2/zfs275@snap    <- instant_clone_qsnapshot
```

QNAP's own CSI driver uses the full-copy variant. The instant clone is what
makes a PVE linked clone instant and nearly free, so that is what this plugin
uses.

`targetIndex` also maps the new LUN to that target as a side effect.

## Offloaded copy (ODX / XCOPY)

The LUNs advertise Third Party Copy on VPD page 0x8f, and the commands list is
not empty:

```
Extended copy(LID1)   Extended copy      Populate token    Write using token
Receive copy status   Receive ROD token information        Report all ROD tokens
```

A token copy between two LUNs on the same NAS works. Verified end to end: write
distinct data to each LUN, `POPULATE TOKEN` on the source, `WRITE USING TOKEN` on
the destination, and the destination then matches the source.

```sh
ddptctl --pt=0,2048  --rtf=token.bin /dev/sdX   # source
ddptctl --wut=0,2048 --rtf=token.bin /dev/sdY   # destination
```

Two caveats found while testing: `EXTENDED COPY (LID1)` is rejected with Illegal
Request, so only the token path works; and the range has to stay within the limits
on VPD 0x8f (a too-large range returns "LBA out of range").

**None of this is reachable from Proxmox.** The kernel exposes no copy offload —
`/sys/block/*/queue/copy_max_bytes` does not exist — and neither QEMU nor Proxmox
issues these commands, so a disk copy is always read-then-write over the network.
It is only listed here so nobody has to re-investigate it.

## Deleting

Order matters:

1. unmap the LUN — `DELETE /api/iscsi/v1/targets/:ti/luns/:li`
2. delete any clones derived from its snapshots
3. delete the snapshots
4. delete the volume — `DELETE /api/storage/v1/volumes/:vid`

Deleting the volume removes the LUN as well.

Two error codes worth recognising:

- `-14 Failed to unmount volume` — **the LUN is still mapped to a target.**
  Nothing is mounted; the message is simply wrong. Check `mapped` in
  `GET /api/iscsi/v1/luns`.
- `-618 Dataset has cloned snapshot` — a clone still depends on a snapshot of
  this volume.

Deleting the LUN *before* the volume orphans the volume: it ends up with
`lun_index: -1` and can no longer be deleted. Recover by registering a LUN for
it again with `POST /api/iscsi/v1/luns` (that endpoint registers an existing
block device — it does not create one) and then deleting the volume.

## Useful read-only endpoints

```
GET /api/iscsi/v1/luns                lun_index, lun_name, blkdev_name, lun_naa, mapped
GET /api/iscsi/v1/targets             target_index, target_iqn, connected initiators
GET /api/iscsi/v1/service             portal settings, max_target_cnt, max_lun_cnt
GET /api/storage/v1/pools             capacity.{capacity_bytes,allocated_bytes,free_bytes}
GET /api/storage/v1/volumes           size.{total,used,free}, lun_index, provision_type
```

`max_lun_cnt` is **255**, which is the hard ceiling on the number of VM disks.

Volumes must be filtered by `volume_type == 3` (zvol). Shared folders appear in
the same collection under a different type.
